# 树莓派摄像头局域网实时推流

把树莓派上的 USB 摄像头画面通过 HTTP 推到局域网，浏览器直接打开就能看，端到端延迟约 60~100ms。

---

## 快速使用

树莓派开机后服务自动启动。在浏览器打开：

```
http://<树莓派IP>:8080/
```

树莓派的地址可以在它本机上查：

```bash
ip -4 addr show | grep inet
```

或者在路由器后台的设备列表里找。

| 路径 | 用途 |
|---|---|
| `/` | 网页播放器（自带延迟测量、状态栏） |
| `/stream` | 裸 MJPEG 流，可直接嵌入 `<img>` |
| `/snapshot` | 当前单帧 JPEG |
| `/state` | 运行状态 JSON |

嵌入自己的网页只要一行：

```html
<img src="http://<树莓派IP>:8080/stream">
```

`--allow-origin=*` 已开启，跨域调用不会被拦。

---

## 网页播放器功能

- **实时画面** — 断线自动重连
- **去畸变预览** — 默认使用本摄像头的棋盘格标定参数显示校正画面，详见下一节
- **调参** — 打开畸变校正的参数面板
- **参考网格** — 叠加一层直线网格，用来判断画面里的直线是否被拉直
- **延迟测量** — 点按钮弹出毫秒级时钟，把摄像头对准屏幕上这块时钟，画面里拍到的时间与真实时间之差就是端到端延迟。这是唯一能测出真实「玻璃到玻璃」延迟的方法
- **保存截图** — 将当前预览帧以 PNG 下载到打开网页的电脑；默认保存去畸变后的画面
- **电脑端录像** — 按开始录像时的预览模式保存 WebM：去畸变预览开启时保存校正画面，关闭时保存原始畸变画面；录像期间锁定模式切换。采集、编码和文件生成全部在观看电脑的浏览器中完成，不占用树莓派算力
- **底部状态栏** — 分辨率、采集帧率、本机接收帧率、链路状态、渲染帧率、当前校正参数

状态栏的**链路**一项是判断卡顿的关键：

| 显示 | 含义 |
|---|---|
| 通畅 | 接收帧率 ≥ 采集帧率的 85%，延迟稳定 |
| 偏紧 | 50%~85%，带宽接近上限 |
| 拥塞 | < 50%，**帧在排队，延迟会持续累积** — 需要降分辨率 |

## 畸变校正

广角 USB 摄像头普遍存在**桶形畸变**：本该是直线的桌沿、门框、天花板在画面里向外鼓成弧线。网页默认显示**去畸变后的预览**，按钮可切换回原始画面，也可点“识别ROI”查看与树莓派钢球识别相同的长条形局部校正坐标。

校正使用同一只摄像头在 1280×720 下采集 17 张棋盘格照片得到的 OpenCV fisheye 标定参数，重投影 RMS 为 0.344 px。网页实现与 OpenCV `cv2.fisheye` 相同的 Kannala-Brandt 四阶模型，不再使用目测的两参数近似模型。

标定适用于 1280×720，也可等比例缩放到 1920×1080。切换到 800×600 或 640×480 等 4:3 模式时，网页会自动显示原始画面，避免使用未经验证的错误校正参数。

### 重要：图传预览校正在浏览器里做

这是个刻意的设计选择。图传预览的校正用 **WebGL 片元着色器在观看端的 GPU 上完成**，树莓派不为图传重新编码：

- 树莓派保持 MJPEG **硬件直通**，CPU 占用仍是 0.2%
- **不增加任何延迟**
- 换分辨率、多人同时观看都不受影响

如果放到树莓派上做，就必须「解码 JPEG → 重映射 → 重新编码 JPEG」，直通被打断，CPU 占用会涨到 150% 以上，延迟增加 20~30ms。

**副作用**：校正只对这个网页播放器生效。`/stream` 和 `/snapshot` 输出的仍是**未校正的原始画面**，把流嵌到别的地方看到的也是原始画面。树莓派钢球识别程序会在解码后使用同一组 OpenCV 参数独立去畸变，不直接使用网页画布。

网页截图和录像都直接来自当前 WebGL 画布。全图校正、原始图和识别ROI分别使用 `undistorted-`、`raw-` 和 `tube-roi-` 文件名前缀，并由浏览器保存到观看电脑。录像以 30fps、约 8Mbps 在电脑端编码为 WebM；树莓派端不会生成录像文件，也不会执行视频编码。

> 树莓派的硬件 ISP（Pi 5 的 PiSP）**不具备**几何畸变校正能力——它的功能是去马赛克、降噪、HDR 合成、色彩处理，没有 dewarp/LDC 单元。而且它只接受 YUV/RGB/Bayer 输入，不接受 JPEG。所以硬件加速这条路走不通。

### 怎么调

默认参数来自棋盘格标定。摄像头和镜头没有重新装配时，通常只需调整 `balance` 和额外缩放；如镜头位置发生变化，可按下面步骤检查和微调：

1. 点**参考网格**，叠加直线网格
2. 点**调参**打开参数面板
3. 让画面里出现一条明确的直线（桌沿、门框、书架边缘），最好横穿整个画面
4. 先恢复标定值，仅在确认旧标定失效后再微调 k1～k4 或光心修正

| 参数 | 作用 |
|---|---|
| **k1～k4** | OpenCV fisheye 四阶畸变系数，默认使用实测标定值 |
| **balance** | 0 裁掉无效边缘并填满画面；1 最大限度保留原始视野，可能出现黑边 |
| **额外缩放** | 在 balance 的基础上继续放大或缩小预览 |
| **光心 X / Y 修正** | 对标定光心进行像素级补偿，仅在镜头重新装配后使用 |

调参技巧：优先恢复标定值并用参考网格检查；不要把网页中的 k1～k4 与普通 Brown-Conrady 模型参数混用。

### 参数保存

参数自动存在浏览器的 localStorage 里，下次打开保持不变。**换浏览器或换设备需要重新调**。

- **恢复标定值** — 回到这只摄像头的棋盘格标定参数
- **复制参数** — 把当前参数复制到剪贴板，方便记录或同步到其他设备

关掉**去畸变预览**按钮即可看原始画面，方便对比校正前后的效果。

## 切换分辨率

树莓派上直接用 `camres` 命令：

```bash
camres                  # 查看当前配置和实际运行状态
camres 1920x1080        # 切到 1080p
camres 1280x720 60      # 同时指定帧率
```

改完会自动重启服务，无需手动操作。

### 各分辨率实测数据（摄像头满速 57fps）

| 分辨率 | 单帧大小 | 实际码率 | 适用场景 |
|---|---|---|---|
| 1920x1080 | 237 KB | ~121 Mbps | 画质优先，需要网络空闲 |
| **1280x720** | **124 KB** | **~58 Mbps** | **默认，余量充足** |
| 800x600 | 77 KB | ~36 Mbps | — |
| 640x480 | 42 KB | ~19 Mbps | 弱网 / 2.4GHz WiFi |

**怎么选**：先测出链路的实际吞吐（见下方 `measure.py`），然后选一个**码率不超过链路吞吐 50%** 的分辨率。留出一倍余量是必要的——WiFi 吞吐会随干扰和其他设备波动，一旦实际码率逼近上限就会开始排队，延迟不再收敛而是持续增长。

参考：在实测 168 Mbps 的 5GHz 链路上，720p 占用 34%（稳定跑满 57fps，零积压），1080p 占用 72%（能跑但余量不足）。

## 部署到新设备

把 `deploy/` 整个目录复制到树莓派，然后：

```bash
cd deploy && sudo bash install.sh
```

脚本会安装 ustreamer、部署所有文件、启用开机自启，最后打印访问地址。

前提是 USB 摄像头已插好且支持 MJPEG 输出。可以先确认：

```bash
v4l2-ctl --list-devices
v4l2-ctl -d /dev/video0 --list-formats-ext | grep -A3 MJPG
```

## 常见问题

**画面卡顿 / 延迟越来越大**

看状态栏「链路」。显示「拥塞」说明带宽不够，用 `camres` 降一档分辨率。这几乎是唯一的原因——MJPEG 的延迟基本等于「一帧数据在网络上传输的时间」。

**`rpicam-hello --list-cameras` 报 "No cameras available"**

正常。USB 摄像头是 **UVC** 设备，而 `rpicam`/`libcamera` 系列工具只管 CSI 排线摄像头。用 `v4l2-ctl --list-devices` 查看。

**换了网络后连不上**

树莓派 IP 可能变了。在路由器后台查，或在树莓派本地用 `ip -4 addr show` 确认。如果需要地址固定，可以在路由器上做 DHCP 静态绑定。

**想提高画质但带宽不够**

改用 H.264 + WebRTC，720p 只需 2~3 Mbps。代价是 Pi 5 **没有硬件 H.264 编码器**，需要软件 x264 编码（约占一个 CPU 核心），且 WebRTC 的抖动缓冲会增加 50~100ms 延迟。5GHz 带宽充足时没必要。

**这个流没有密码，同局域网任何人都能看**

如需鉴权，可在前面加一层带 Basic Auth 的 nginx 反向代理。

## 本地工具脚本

`tools/` 下是开发调试用的辅助脚本，需要 `pip install paramiko`。

先设置连接信息（不写死在代码里）：

```powershell
# PowerShell
$env:RPI_HOST = "树莓派的IP"
$env:RPI_USER = "登录用户名"
$env:RPI_PASS = "登录密码"
```

```bash
# bash
export RPI_HOST=树莓派的IP RPI_USER=登录用户名 RPI_PASS=登录密码
```

然后：

```bash
# 在树莓派上执行命令（命令通过 stdin 传入，避免转义问题）
echo "systemctl status ustreamer" | python tools/rpi.py

# 上传文件到树莓派（自动 sudo 放置到目标绝对路径）
python tools/upload.py 本地文件 /远程/绝对路径

# 测量推流的实际吞吐与到达帧率
python tools/measure.py [测量秒数]
```

`measure.py` 是判断分辨率选得合不合适的主要依据：**到达帧率应当接近服务端采集帧率**，明显偏低就说明链路吃紧。
